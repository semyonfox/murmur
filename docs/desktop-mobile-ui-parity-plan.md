## Wispr Flow Android reference · 29 September 2026

This comparison uses Wispr's documentation and nine screenshots supplied from a phone, not a live walkthrough on the laptop. Wispr Flow's [Android installation guide](https://docs.wisprflow.ai/articles/2809924024-android-download-installation-guide) directs users to Google Play. It has four position dots, no arrow controls, and leaves part of the transcript list visible below. Murmur's Android and desktop Stats now have the same swipe/scroll and dot pattern. Wispr's card gives one number and one plain-language explanation plenty of room, but its height means little history fits on the first screen. Keep Murmur's metric cards shorter where possible, with a clear label and one concise explanation; retain charts and cost below the cards rather than folding them into the carousel.

The screenshots also show date headings over transcript cards with Copy, Report and overflow actions; a four-item bottom dock for Home, Dictionary, Style and Snippets; searchable Dictionary and Snippets lists; and Style segmented by Personal, Work, Email and Other with a sample message. The useful ideas for Murmur are day-grouped history, search where user-maintained lists grow, and an example beside a style choice. Copy and deletion already exist in Murmur history. Report is a service-specific action, so copying that control would add no useful local behavior. Do not copy Wispr's dock literally: Murmur needs visible routes for recognition, lectures, stats, privacy and input setup, which do not map to those four tabs.

The supplied accessibility-permission screen uses numbered instructions, illustrations and one Open settings button. That makes the Android settings path concrete, but its large illustrations and whitespace hide progress and the remaining setup steps. Murmur's readiness checklist is a better base for its local and online recognition choices. Improve it with a direct settings action and a short return-to-app instruction for each unresolved permission, then clear the warning when Android confirms success. These screenshots do not establish how Wispr's bubble behaves in other apps or how its first-run flow proceeds end to end.

Platform controls can use native layouts. Desktop shortcuts, Android accessibility and keyboard setup, and device-specific audio effects need their own controls.

## UI direction

Start with setup. Home should show a small progress card with the remaining steps and direct links: allow microphone, choose a recognition source, then enable the bubble or keyboard for text-field dictation. Lecture-only setup can skip the input method, but still needs a working recognition source and microphone access for recording. The recognition step must offer downloaded/on-device speech alongside a configured endpoint; it should not imply that an API key is always required. Do not show “ready” until the selected path can actually perform the action named on the screen.

Keep the desktop sidebar and Android dock, but make the content structure recognizable across platforms. Use the same page titles, section order, card headings, tone names and privacy explanations. On Android, separate the current long Recognition form into clear local and online choices; show detailed fields for the chosen path. Use distinct groups for local filler removal, optional AI cleanup and instructions. Keep the final Save action reachable after scrolling and avoid presenting obscured controls as if they are unavailable.

The desktop render is stronger at compact grouping and showing the full navigation map. Android is stronger at readable touch targets, direct action labels and plain data-boundary explanations. Its long Recognition, Cleanup and Input pages make setup feel scattered. The preferred direction is the desktop's scannable sections with Android's larger controls and direct copy, not a literal copy of either platform's screen size or navigation chrome.

Test recording, insertion, local inference and provider paths only with synthetic data and explicit endpoints. Repeat Android input checks on a physical device before claiming supported behavior there.

## Acceptance criteria

- Every shared choice has the same meaning, default, name and reachable action on both apps.
- On a fresh install, the app shows every required setup step, its current state and the next action. The user can choose local recognition without being directed to add an API key.
- Shared pages follow the same conceptual order: recognition, cleanup, dictionary, history, lectures, stats, and input settings, with platform controls explained in place.
- Raw transcripts remain recoverable under each platform's retention rules. The UI states precisely when audio or text leaves the device.
- No screen hides its final actions behind the mobile dock or clips controls at the desktop window's supported size.
- Empty, loading, disabled and error states are checked on both clients. A screenshot set and a control matrix show the result; untested paths are labelled as such.
