# Android client

Murmur has a native Kotlin Android client. On Android 13 and newer, an optional voice bubble appears beside a focused, editable field while the user's usual keyboard remains selected. The idle control is a compact microphone icon; drag it to move it or tap to start recording. It expands for recording and transcription, with Done and × actions. Input settings save its size, opacity and position. The Murmur keyboard remains an alternative on Android 8–12 and on newer phones where the bubble does not work well. See the [setup and build guide](../apps/android/README.md).

## Current dictation path

1. In Murmur, set an STT endpoint and model, save a key if needed, and allow microphone access. The default is OpenRouter's /audio/transcriptions endpoint with openai/whisper-large-v3-turbo. The client sends a temporary WAV recording as an OpenAI-style multipart request and expects JSON containing text. It accepts HTTPS endpoints and HTTP only on the phone's own loopback address. A PC's localhost is not the phone's localhost. [OpenRouter STT guide](https://openrouter.ai/docs/guides/overview/multimodal/stt), [Android network security configuration](https://developer.android.com/privacy-and-security/security-config).
2. For the bubble, accept the in-app Accessibility disclosure and enable **Murmur voice bubble** in Android settings. Then return to the visible Murmur activity and tap **Turn on voice bubble** in the status card. This starts a microphone foreground service and posts a notification with a Stop action. Android restricts starting this service from a background bubble because microphone access is a while-in-use permission. [Foreground-service restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start).
3. Focus an ordinary text field. The service checks the focused node and editor type before showing its compact accessibility overlay above the detected keyboard. Dragging saves a position within the visible space above the keyboard; rotation or a keyboard change clamps it back into view. It suppresses the bubble in password, number, phone, and fields marked to disable personalized learning. Its TYPE_ACCESSIBILITY_OVERLAY does not need the separate draw-over-other-apps permission. [Accessibility service guide](https://developer.android.com/guide/topics/ui/accessibility/views/service), [overlay window type](https://developer.android.com/reference/android/view/WindowManager.LayoutParams).
4. The recorder captures up to two minutes of audio. After transcription, Murmur checks that the focused node and editor still match the recording target, then sends text with AccessibilityInputConnection.commitText. It reads cursor context for spacing but does not send existing field text to the STT endpoint. The latest raw transcript stays recoverable if the target changed or the send failed. Android does not return an insertion-success result from this API, so on-device testing must verify that apps actually accept the text. The Android 13 accessibility input method API is why the bubble has an Android 13 minimum. [Accessibility input method API](https://developer.android.com/reference/android/accessibilityservice/InputMethod), [commitText API](https://developer.android.com/reference/android/accessibilityservice/InputMethod.AccessibilityInputConnection).

The optional Murmur keyboard uses Android's InputMethodService and InputConnection.commitText instead. It cancels recording when its input view closes or the editor changes. This is the path for Android 8–12. [Platform IME guide](https://developer.android.com/develop/ui/views/touch-and-input/creating-input-method).

Android may block Accessibility for a sideloaded APK until the user opens **Settings → Apps → Murmur → More → Allow restricted settings**. The user should only do this for an APK they trust. [Android restricted settings](https://support.google.com/android/answer/12623953?hl=en). A Google Play release needs an accurate Accessibility API declaration and prominent disclosure and consent; the current setup screen supplies the disclosure, but Play review has not happened. [Google Play Accessibility policy](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en).

## Lecture and audio-file path

History has a lecture card with **Record lecture** and **Choose audio**. Recording runs in a microphone foreground service with a persistent Finish action. Android decodes imported files to 16 kHz mono WAV. Both paths cap audio at eight hours, store it in app-private storage, and send at most two minutes per transcription request. Optional cleanup receives each text part after its raw transcript is saved. The app retains partial text and audio after a failed request, with a manual Retry action. Retry can create new provider charges. Saved audio can be shared separately; the JSON export contains text only. The phone's on-device speech recognizer cannot process saved audio, so the lecture actions require explicit endpoint recognition.

## Data and model limits

The Android app now offers the system's on-device recognizer when available, as an explicit alternative to its configured speech endpoint. The Speech section has separate Recognition and Cleanup screens with visible status. It also has optional transcript cleanup through an OpenAI-compatible chat endpoint, a preferred-spelling dictionary, text history, recorded WPM and optional Android noise suppression. Cleanup is separate from recognition: a cloud cleanup provider receives raw text and dictionary entries, while the speech endpoint receives audio only when selected. Failed cleanup uses raw text, which remains recoverable in history, and the last failure is shown on the Cleanup screen. On-device recognition does not silently switch to cloud. The app encrypts both BYOK keys with Android Keystore AES-GCM and removes a saved key when its endpoint URL changes. Short dictation WAV files are deleted after processing. Lecture WAV files stay in private storage for retry and sharing until their retention period ends or the user deletes them. A compatible service on another machine needs HTTPS; a phone's `localhost` is not a desktop server.

OpenRouter's cleanup-model routing does not establish where a speech request runs. Its STT guide says BYOK is supported, but provider.order, only, and ignore preferences do not apply to transcription requests. Do not claim that the current Whisper request runs on SiliconFlow without checking the actual STT provider route. [OpenRouter STT routing notes](https://openrouter.ai/docs/guides/overview/multimodal/stt).

The current local mode uses Android's [on-device SpeechRecognizer](https://developer.android.com/reference/android/speech/SpeechRecognizer) on phones with an installed service. It cannot select or inspect that service's model and does not work on every phone. A separately packaged arm64 model remains future work: measure accuracy, latency, memory and battery on real devices, then download weights on demand with checksum and license checks. The [model study](research/models-and-cleanup.md) covers candidates. A user-selected model file could come through the [document picker](https://developer.android.com/training/data-storage/shared/documents-files) when the runtime can use its file descriptor.

Cleanup now has a separate text stage, preferred-spelling dictionary and five formality levels, but its prompt and output checks still need an on-device quality evaluation against the desktop fixtures. The app stores raw and final text in SQLite with optional 7, 30 or 90 day retention and user-triggered JSON export. Home shows retained words, current-week words, recorded WPM and minutes, eight weeks of word totals and weekly pace. Spoken WPM uses raw words and recorded duration, including pauses. Lecture audio retention and retranscription are available in History. Playback, compressed archive export and separate STT/cleanup usage accounting remain to be built. The [data and stats contract](data-and-stats.md) describes the intended fields.

## Verification still needed

The source and build instructions are in the [Android app README](../apps/android/README.md). A successful Gradle build, unit tests, or lint cannot establish that the accessibility bubble behaves correctly across Android devices. On an Android 14/API 34 x86_64 emulator, the popup stayed above the stock keyboard, captured a 488,810-byte WAV, sent it to a loopback mock STT endpoint, and inserted the mock transcript at the cursor. The bubble stayed hidden in an Android Wi-Fi password field, and the [recording pill](screenshots/android-popup-api34.png) showed its full timer and Done action. This run used no real keys or external API calls.

Physical arm64 coverage and the Gboard/app matrix remain pending. The lecture service, long microphone capture, imported audio decoder, screen-off operation, retention and retry path also need device testing. Test bubble dragging, opacity and size changes, Gboard and another keyboard, Chrome/WebView, chat composers, password and numeric fields, selection replacement, editor switches during transcription, rotation, split screen, floating keyboards, permission revocation, no network, notification Stop, and force stop. Verify the bubble's position above each keyboard and that stale results never reach a different field. The IME fallback needs the same insertion and lifecycle checks on Android 8–12. [Android command-line testing](https://developer.android.com/studio/test/command-line), [device testing](https://developer.android.com/studio/run/device).
